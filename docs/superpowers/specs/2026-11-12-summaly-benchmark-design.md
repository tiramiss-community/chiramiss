# summaly との比較ベンチマーク 設計

## 目的と背景

chiramiss が upstream summaly より速く、負荷をかけにくいことを README で外部に示したい。
README に載せたい主張は次の 3 つ。

1. 同じページを X 倍速く要約する
2. 同時アクセスが多くても応答が速い
3. 自分側（要約サーバ）にも対向先（要約されるサイト）にも負荷がかかりにくい

数字は第三者が同じコマンドで再現できなければならない。比較相手は summaly の公式 Docker イメージ。

## ゴール / 非ゴール / アンチゴール

**ゴール**
- 1 コマンドで、chiramiss（手元のソースからビルド）と summaly（公式イメージ、版を固定）を同一条件で測り、
  README に貼れる Markdown の表と、生データ（JSON）を出す。
- 結果に測定環境・chiramiss のコミット・summaly の版を必ず添える。
- 第三者が同じコマンドで同程度の倍率を再現できる。

**非ゴール**
- CI での自動計測（GitHub Actions のランナーは同居ジョブで数字がぶれるため、やらない）。
- リグレッション検知のための継続計測。
- 実サイトでの計測。

**アンチゴール（技術的に動いても失敗とみなすもの）**
- 第三者の実サイトにリクエストを送ること。ベンチマークで他人のサイトに DDoS まがいの負荷をかけない。
  対向先はすべてローカルの偽サーバにする。
- chiramiss に有利な条件を黙って混ぜること（キャッシュが効いた結果を「単発の速さ」として載せる、など）。
  効いている最適化は結果と一緒に明示する。
- 測定時だけ chiramiss の本番と違うコード経路を通ること。

## 決まったこと（ユーザーの決定）

- 対向先はローカルの偽サーバのみ。実サイトは使わない。
- 比較相手は summaly の公式 Docker イメージ `ghcr.io/misskey-dev/summaly`。
- chiramiss 側は公開イメージではなく、手元のソースからビルドしたイメージで測る。
  リリースタグを切ったなど特定の時点で測って README を更新する運用。
- 手元で実行し、出力された表を README に貼る。CI では回さない。
- 計測項目（ページの種類・シナリオ・公平さの決めごと）は下記の案で合意済み。

## 構成

docker compose で次の 4 つを同じ Docker ネットワーク上に置く。

- **origin**: 偽の対向サーバ。決まった内容を返し、受けたリクエスト数と送ったバイト数を数える。
- **chiramiss**: リポジトリの `Dockerfile` から手元でビルドしたイメージ。
- **summaly**: `ghcr.io/misskey-dev/summaly:<固定した版>`。
- **loadgen**: 負荷をかけ、結果を集計するクライアント。

両要約サーバの API は同じ（`GET /?url=...&lang=...`）なので、同じ負荷スクリプトをそのまま向けられる。

### プライベート IP ブロックの外し方（公平さに関わる）

偽サーバは Docker ネットワーク上のプライベート IP にいるため、両者ともブロックを外す必要がある。

- summaly: `SUMMALY_ALLOW_PRIVATE_IP=true`。summaly はレスポンス受信後に IP を確認するだけなので、
  外しても処理の流れはほぼ変わらない（summaly 自身の Docker テストも同じ方法）。
- chiramiss: `CHIRAMISS_ALLOW_PRIVATE_IP=true` は**使わない**。これを立てると Node の global agent 経由になり、
  本番の接続再利用の経路を通らなくなる。代わりに `CHIRAMISS_ALLOWED_PRIVATE_NETWORKS` にベンチ用ネットワークの
  CIDR だけを入れ、本番と同じ経路のまま偽サーバに届くようにする。
  そのためベンチ用ネットワークのサブネットは compose で固定する。

### 条件をそろえる

- 両要約サーバのコンテナに同じ CPU 数・メモリ上限をかける（具体値はビルダーの判断。既定値を決め、引数で変えられるようにする）。
- 両者は同時には走らせず、片方ずつ測る（同じホスト上で CPU を奪い合わないため）。
- 両者のタイムアウト・サイズ上限・`followRedirects` などの設定は明示的に同じ値にそろえる。
- 各シナリオの前に暖機運転を入れ、各シナリオを複数回走らせて、ばらつきも結果に出す。
- 偽サーバは固定の遅延（例: 50ms）を入れて、実ネットワーク越しに近い状況にする。
  （私の判断）遅延はレスポンスごとの sleep ではなく、**往復遅延（RTT）として TCP の接続確立にもかかる形**で入れる。
  keep-alive による接続再利用は接続確立の往復を省く最適化なので、sleep だけだと実運用で効く差が数字に出ない。
  手段は `tc netem`（origin 側に NET_ADMIN）か、ユーザ空間の遅延 TCP プロキシか、ビルダーの判断
  （対象環境のすべてで同じ挙動になること）。
- （私の判断）偽サーバは **HTTPS** で立てる。実サイトはほぼ HTTPS で、TLS ハンドシェイクのコストは接続再利用の差や
  自分側の CPU 時間に直接効くため。ベンチ用の自己署名 CA を作り、両コンテナに `NODE_EXTRA_CA_CERTS` で信頼させる
  （本番のコード経路は変わらない）。
- （私の判断）`followRedirects` は両者とも **true** にそろえる（環境変数 `CHIRAMISS_FOLLOW_REDIRECTS` /
  `SUMMALY_FOLLOW_REDIRECTS`）。false ではリダイレクトページを比べる意味がないため。

### 対象環境（私の判断）

再現手順が保証する環境は **Linux 上のネイティブ Docker（cgroup v2、amd64 / arm64）** とする。WSL2 上の Docker Engine は
これに含む。Docker Desktop（macOS / Windows）は動けばよいが保証しない。summaly の公式イメージは amd64 / arm64 の両方が
出ているので、arm64 でもエミュレーションなしで比較できる。前提はベンチの README に書く。

## 偽の対向サーバが返すページ

- **普通の記事ページ**: OGP あり、数十 KB。
- **大きいページ**: 1〜2 MB。`<head>` の後ろに長い本文。chiramiss が `<head>` 中心にしか読まない効果が出る。
- **Shift_JIS のページ**: 文字コード判定のコスト差が出る。
- **oEmbed と favicon を持つページ**。
- **リダイレクトを 1 回挟むページ**。

ページ内容は生成スクリプトではなく、リポジトリに固定のフィクスチャとして置くか、固定シードで決定的に生成する
（どちらにするかはビルダーの判断。毎回同じバイト列になることが条件）。

## シナリオ

1. **単発の速さ（キャッシュなし）**: URL に連番クエリを付けて毎回別ページ扱いにし、1 件ずつ順番に要約させる。
   ページ種類ごとに中央値・p95。**README の「X 倍速い」はこのシナリオの数字を使う。**
   遅延なし（0ms）と遅延あり（例: 50ms RTT）の 2 条件で走らせる。

### README の見出しの数字（ユーザーの決定）

- 見出しは **遅延なし・普通の記事ページ** の中央値の比で、「要約処理そのものが X 倍速い」と書く。
- 併記するもの: ページ種類ごとの倍率の幅（最小〜最大倍）と、遅延ありの結果の表。
  都合のよい 1 つだけを見せていると取られないよう、条件（遅延なし＝要約処理そのものの比較）を見出しのすぐそばに書く。
2. **同時アクセス（キャッシュなし）**: 毎回別の URL で、同時接続数 1 / 10 / 50 / 100。
   毎秒の処理件数、p50 / p99、エラー率。
3. **同じ URL への集中**: 1 つの投稿が多数のタイムラインに流れた状況を想定し、同じ URL へ N 件。
   偽サーバが受けたリクエスト数・送ったバイト数と、応答時間。「対向先に優しい」の根拠。
   （私の判断）次の 2 つに分け、表でも別の行にして、どちらの効果かを明記する。
   - **3a 同時着**: N 件をほぼ同時に送る。chiramiss の「同時に走っている取得の共有」だけが効く。
   - **3b ばらけて到着**: N 件を一定時間（例: 10 秒）に散らして送る。共有に加えて結果キャッシュ（既定 5 分）も効く。
   いずれも暖機・繰り返しのたびに URL を変え、毎回キャッシュが空の状態から始める。
4. **自分側の負荷**: 1〜3 の各シナリオ中の、要約サーバコンテナの CPU 時間とメモリのピーク。

1・2 でキャッシュが効いていないことは、偽サーバ側のリクエスト数（1 要約あたりのページ取得が 1 回以上あること）で確かめ、
結果にも載せる。

### 効いている最適化の明示（私の判断）

シナリオ 1・2 は URL をクエリで変えるが、ホストは同じなので、chiramiss の「同じサイトへの keep-alive 接続の再利用」や
「favicon 確認結果のキャッシュ」は効く。これは実運用でも同じサイトの別記事に対して効く本番の挙動なので、そのまま測る。
ただし結果の注記に「何が効いているか」を書き、隠さない。

## 出力

- 生データ: JSON（ラン単位、シナリオ単位）。
- README 用: Markdown の表。各表に次を添える。
  - 測定日時、ホストの CPU / メモリ / OS、Docker のバージョン、コンテナにかけた CPU / メモリ上限
  - chiramiss のコミット（ハッシュと、あればタグ）、作業ツリーが汚れていればその旨
  - summaly のイメージの版（タグと digest）
- 結果ファイルの置き場所・名前の付け方はビルダーの判断。

## 実行方法

- ルートから 1 コマンドで、イメージのビルド/取得 → 起動 → 全シナリオ → 集計 → 後片付け まで行う。
  コマンド名はビルダーの判断（例: `pnpm bench`）。
- summaly の版は既定値を 1 つ固定し、引数や環境変数で差し替えられるようにする。
  既定値は **`ghcr.io/misskey-dev/summaly:5.6.0`**（ユーザーの決定）。summaly の Docker イメージ公開は 2026-11-11 に
  追加されたばかりで、まだ 1 つも公開されていない（5.5.2 の時点には Dockerfile もない）。最初の公式イメージは
  次のリリース 5.6.0 になる見込みなので、ベンチは先に作り、README の数字は 5.6.0 の公開後に測る。
- （私の判断）Node.js の版の違いが結果に混ざらないよう、chiramiss は summaly のイメージと同じ Node.js の版の
  `node:<版>-slim` を `NODE_IMAGE` に渡してビルドする（版は summaly のイメージで `node -v` を実行して得る）。
  結果には両コンテナの Node.js の版を載せる。
- 実行時間の目安を README（または bench の README）に書く。

## ビルダーに任せること

- ベンチのコードを置く場所（ルート直下のディレクトリか、ワークスペースパッケージか）。
- 負荷生成の手段（自作スクリプトか既存ツールか）。ただし実行環境の差が出ないよう、コンテナ内で動かすこと。
- 偽サーバの実装、フィクスチャの作り方。
- CPU / メモリ上限、同時接続数ごとのリクエスト数、暖機の量、繰り返し回数、シナリオ 3 の N の具体値。
- CPU 時間・メモリピークの取り方（cgroup の値を読む、`docker stats` など）。
- 表のレイアウト。
